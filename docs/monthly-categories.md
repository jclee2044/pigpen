# Monthly categories — implementation contract, November 22, 2026

Confirmed: category inclusion is scoped to the selected month; the action is labeled **Remove**; no archived-category list is exposed. Purchase category options follow the transaction month, including backdated entries. Historical allocations and purchases remain reportable. The dropdown ends with **Other**, revealing required **Please explain** text.

Implementation defaults: retain shared category identity, names, hierarchy and ordering. Membership snapshots are independent once a month has a budget edit, category edit, purchase, income or savings activity. Unestablished months preview the latest earlier established setup. Reading does not create records. Removing a parent removes its children from that month's choices; adding a parent does not automatically re-add children. Personal parents remain protected; Savings retains its existing financial semantics. Other is an always-available, protected shared expense category with a dedicated explanation on each purchase, not an automatically generated category name.

## JSON contract (before client integration)

- New synchronized resource `category-months`: normal record fields plus `month`, `category_ids` (included UUIDs), `inherited_allocations` (category_id/amount_minor pairs), `inherited_income_minor`. Its revision serializes membership changes and budget changes for that month. Existing category, purchase and allocation IDs are preserved.
- `category.include`: category entity ID; `{month, included, expected_revision}`. Revision is the category-month revision, or 0 for an unestablished month. A conflicting revision returns 409 without changes. Removal preserves the month's inherited plan and existing allocations; future previews exclude removed allocations. New entries are rejected for removed categories. Historical purchase edits may keep the same category in the same month.
- `category.create` adds optional `month` and `month_revision`. Legacy callers without month create in the household's current month only. Explicit month callers provide its revision (0 if new). `category.update` continues rename/capability edits; attempts to change global `active` return an update-required conflict. Global archival is no longer a category-management action.
- Purchase payloads/records add `category_explanation` (up to 4000 characters, default empty for compatibility). Other requires nonblank text, validated server-side for manual, offline and receipt purchases. Non-Other purchases reject nonempty explanations. Other is identified by reserved stable UUID `00000000-0000-5000-8000-000000000001`, not by display name. Existing categories named Other are not merged.
- Missing monthly membership returns `category_unavailable` (409) with `{month, category_id}`. Queued operations remain durable; the UI offers explicit add-and-retry. Replays preserve original operation IDs and actor. New optional defaults are omitted from legacy payload hashes to preserve idempotency.
- Bills retain their category identity; recording payment checks its transaction month. Approval requests retain category links independently of month; purchase completion validates membership. Parent/child budgets roll up once.

## History and migration

The additive migration establishes monthly membership and frozen inherited amounts for every elapsed month from the earliest recorded budget/financial month through the household current month, plus recorded future months. Saved allocations and purchase-linked categories/parents inform historical membership; current/future inclusion starts from globally active categories. Original category availability in old months was not recorded and cannot be exactly reconstructed. No purchases or allocations are rewritten. All existing financial totals must match before/after migration. Other is added without allocation or spending.

Before a mutation affecting inheritance, elapsed months through the household current month are frozen using the pre-edit state. Future months already established by financial activity or edits remain independent; unestablished future months continue to preview the latest earlier setup. An empty membership is explicit, not a signal to inherit. Historical amounts remain visible even for removed categories; no archived collection is displayed.
